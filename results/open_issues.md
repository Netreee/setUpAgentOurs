# 悬置问题清单

更新时间：2026-04-13

---

## 1. 选择器 vs 合成器缺乏公平对比

**现状**：选择器（prod 分支）在暖启动 xpu26 上 B=73.3%，合成器（exp 分支）在同库上 B_synth=73.3%，看似相同。但合成器冷启动（E=46.7%）远低于选择器暖启动，这里冷/暖和选择器/合成器两个变量同时变化，无法归因。

**需要**：在同一个库、同一个 telemetry 状态下，分别跑选择器和合成器各一次（至少在 xpu26 暖启动 + xpu_cold 冷启动两个条件下各跑一组）。

**优先级**：高——直接决定论文最终方案。

## 2. xpu26 数据库被污染（421→574）

**现状**：G 组入库时 index 脚本误将 153 条强模型 XPU 写入 xpu26（.env 中默认 dns 覆盖了命令行传入的值）。

**影响**：原始消融 A/B/C/D 结果不受影响（跑在 421 条时），但后续如需在 xpu26 上追加实验需先恢复。

**修复**：从 `data/xpu26_full_dump.jsonl`（421 条完整导出）恢复，或删除 id 以 `xpu_strong_` 开头的条目。

**优先级**：中——数据卫生问题，不影响已有结论。

## 3. 人工噪声的生态效度

**现状**：膨胀库的 1465 条噪声通过 4 种策略生成（上下文扰动 35%、交叉嫁接 25%、泛化模糊 25%、跨语言干扰 15%），不一定反映真实知识库增长的噪声模式。

**风险**：RetrieverAgent 在人工噪声下 +13.3pp 的结论推广到真实场景时可能打折。

**缓解**：论文中明确说明噪声构造方法，讨论与真实场景的差异。或收集真实的大规模知识库做验证。

**优先级**：低——论文可通过讨论缓解，不阻塞实验。

## 4. 样本量不足（30 repo）

**现状**：30 个 repo 中全 pass 15 个、全 fail 4 个，真正的翻转区只有 6-8 个。1 个随机系统异常 = 3.3% pass 率波动。openqasm 连续两次运行结果不同。

**影响**：小样本结论的置信度不足，尤其是 ±6.7pp 的差异可能在噪声范围内。

**缓解方案**：
- 增大到 100 repo（benchmark_100 已有基础数据）
- 或每组跑 3 次取多数投票

**优先级**：中——增大样本量需要更多计算资源和时间。

## 5. 强模型 XPU + telemetry 积累的叠加效果未测

**现状**：G 组（强模型 558 条冷启动）= 60%。弱模型 + telemetry 积累（F 小库）= 46.7%。但"强模型 + telemetry 积累"的组合未测，这是理论上界。

**需要**：在 xpu_strong 上跑 299 个 repo 积累 telemetry，然后测试。耗时约 18 小时。

**优先级**：低——锦上添花，不影响核心结论。

## 6. 审计机制的真正价值仍未充分验证

**现状**：
- 小库 E=F=46.7%（telemetry 无差异）
- 膨胀库 E=50% < F=56.7%（+6.7pp）

膨胀库的结论受人工噪声影响（问题 #3）。自然增长库上的验证需要先跑几百个 repo 积累真实 telemetry。

**与问题 #5 的关系**：如果做了 #5，同时也解决了 #6。

**优先级**：低——和 #5 一起做。

## 7. 合成器的随机不稳定性

**现状**：
- openqasm：合成器 v1 pass → v2 全量 error
- mopidy：v2 单跑 error → v2 全量 pass
- improv/platformio-core：在不同实验中翻转

选择器（prod 分支）似乎更稳定，但缺乏直接对比数据（问题 #1）。

**可能原因**：合成器额外的 LLM 调用（合成+审计）引入更多采样随机性。

**缓解方案**：temperature=0（已在用），或多次采样投票。

**优先级**：中——影响论文可信度。
